# 대규모 수족관 성능 계획

## 현재 적용 — 수천~수만 마리

- 전체 작품 행을 받지 않는다. `count`와 가장 큰 `world_x`만 조회해 월드 크기를 계산한다.
- `(status, world_x)` 인덱스로 현재 카메라 주변 범위만 조회하며 요청당 최대 300마리다.
- 조회 범위를 1,600px 타일로 맞춰 드래그 매 픽셀마다 요청하지 않는다.
- 최근 12개 범위 요청을 캐시하고 같은 범위의 진행 중 요청도 재사용한다. Realtime 변경 시 캐시를 비운다.
- 받은 작품 중에서도 실제 뷰포트 밖은 DOM과 RAF 애니메이션에서 제외한다.
- 사용자 스프라이트는 픽셀 DOM 대신 래스터 이미지 한 노드로 표시한다.

목표 지표:

- 공개 바다 범위 응답 p95 200ms 이하
- 화면 생물 DOM 150개 이하
- 한 범위 응답 500KB 이하
- 애니메이션 프레임 작업 8ms 이하

## 10만 마리 이상

1. 정확한 전체 `count(*)` 대신 구역별 통계 테이블을 트리거로 갱신한다.
2. 한 타일이 300마리를 넘으면 `world_x + id` 키셋 페이지네이션을 사용한다.
3. 줌아웃 상태에서는 개별 작품 대신 타일별 개수·대표 생물만 보내는 서버 LOD를 적용한다.
4. Realtime 전체 테이블 구독을 현재 카메라 타일 채널 또는 짧은 폴링으로 좁힌다.

## 100만 마리 이상

- 공개 바다 읽기 API를 Edge/CDN 타일 응답으로 분리한다.
- 스프라이트를 WebGL 텍스처 아틀라스로 묶어 DOM 대신 단일 캔버스에서 렌더한다.
- 오래된 작품은 콜드 파티션으로 분리하고 검색·공유 딥링크로만 직접 조회한다.

단계 전환은 추측으로 하지 않고 Supabase 쿼리 p95, 응답 바이트, 화면 RAF 시간을 운영 지표로 수집한 뒤 결정한다.
